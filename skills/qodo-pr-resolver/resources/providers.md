## Provider Detection

Detect the git provider from the remote URL:

```bash
git remote get-url origin
```

Match against:
- `github.com` → GitHub
- `gitlab.com` → GitLab
- `bitbucket.org` → Bitbucket
- `dev.azure.com` → Azure DevOps
- `.gitreview` file or port `29418` or `googlesource.com` → Gerrit (see [gerrit.md](./gerrit.md))

## Cross-cutting principles

These apply across all providers. Per-provider docs assume them.

### Pass bodies via file

Inline body forms (`-f body='…'`, `--body '…'`, `-d '{"content":"…"}'`) hit shell-quoting hazards — backticks, `$`, newlines silently corrupt `@mentions`/markdown. Write each body to a temp file (e.g. `.git/<name>.md` or `.json`), pass with `-F body=@<path>` / `--body-file <path>` / `-d @<path>`, and delete the file after.

Also scan reply text for `#\d+` patterns before posting — GitHub auto-links these to PRs/issues, so Qodo's "Item 2" / "Item 3" references get misrendered; reword (`item 2`) or escape (`\#2`).

### Reply format

- **Fixed:** `✅ **Fixed** — <brief description of what was changed>`
- **Deferred:** `⏭️ **Deferred** — <reason for deferring>`
- Cite Qodo items by title, not number — e.g. `Item 2 ("Unnecessary heavy module import")`, not bare `Item 2`. Qodo renumbers items between passes as issues resolve and new ones appear; bare numbers rot, titles are stable.

### Summary format

```markdown
## Qodo Fix Summary

Reviewed and addressed Qodo review issues:

### ✅ Fixed Issues
- **Issue Title** (Severity) - Brief description of what was fixed

### ⏭️ Deferred Issues
- **Issue Title** (Severity) - Reason for deferring

---
[![Qodo](https://www.qodo.ai/wp-content/uploads/2025/03/qodo-logo.svg)](https://qodo.ai)
Generated by Qodo PR Resolver skill.
```

### Atomic Publish rationale

Chain push, summary post, inline replies, and Qodo-comment reaction into a single `&&`-short-circuited command so webhook-driven bots (Qodo included) see the push and the acknowledgments in the same event window. Without this, the bot's re-scan may re-flag the just-fixed issues. Order: push → summary → replies → reaction. `&&` short-circuit means a failed push doesn't leave a summary citing unpushed commits.

Per-provider chained commands live in each provider doc under `## Atomic Publish (push + summary + replies)`.

## Per-operation reference

For each operation, see the per-provider doc.

### Find Open PR/MR

Get the PR/MR number for the current branch:
- [GitHub](./providers-github.md#find-open-prmr) · [GitLab](./providers-gitlab.md#find-open-prmr) · [Bitbucket](./providers-bitbucket.md#find-open-prmr) · [Azure DevOps](./providers-azure.md#find-open-prmr) · [Gerrit](./gerrit.md#find-open-change)

### Fetch Review Comments

Qodo posts **summary comments** (PR-level), **inline review comments** (per-line), and on GitHub a **review submission body** (`pulls/<n>/reviews`). Fetch all three. **Run the calls in parallel** — fire each provider command as a separate tool call in a single assistant message rather than serializing them. On rate-limit (403), retry just the failed call.
- [GitHub](./providers-github.md#fetch-review-comments) · [GitLab](./providers-gitlab.md#fetch-review-comments) · [Bitbucket](./providers-bitbucket.md#fetch-review-comments) · [Azure DevOps](./providers-azure.md#fetch-review-comments) · [Gerrit](./gerrit.md#fetch-review-comments)

### Reply to Inline Comments

Use the inline comment ID preserved during deduplication to reply directly to Qodo's comments. See § Pass bodies via file and § Reply format above.
- [GitHub](./providers-github.md#reply-to-inline-comments) · [GitLab](./providers-gitlab.md#reply-to-inline-comments) · [Bitbucket](./providers-bitbucket.md#reply-to-inline-comments) · [Azure DevOps](./providers-azure.md#reply-to-inline-comments) · [Gerrit](./gerrit.md#reply-to-comments)

### Post Summary Comment

After reviewing all issues, post a summary comment to the PR/MR. See § Summary format and § Pass bodies via file above.
- [GitHub](./providers-github.md#post-summary-comment) · [GitLab](./providers-gitlab.md#post-summary-comment) · [Bitbucket](./providers-bitbucket.md#post-summary-comment) · [Azure DevOps](./providers-azure.md#post-summary-comment) · [Gerrit](./gerrit.md#post-summary-comment)

### Edit Posted Summary in Place

If a posted summary or reply renders incorrectly (broken code block, unescaped backticks, mangled `@mentions`), use the provider's PATCH/PUT endpoint to fix it in place rather than delete-and-repost. Preserves the comment URL so any references the user already shared stay valid.
- [GitHub](./providers-github.md#edit-posted-summary-in-place) · [GitLab](./providers-gitlab.md#edit-posted-summary-in-place) · [Bitbucket](./providers-bitbucket.md#edit-posted-summary-in-place) · [Azure DevOps](./providers-azure.md#edit-posted-summary-in-place)

### Atomic Publish (push + summary + replies)

See § Atomic Publish rationale above.
- [GitHub](./providers-github.md#atomic-publish-push--summary--replies) · [GitLab](./providers-gitlab.md#atomic-publish-push--summary--replies) · [Bitbucket](./providers-bitbucket.md#atomic-publish-push--summary--replies) · [Azure DevOps](./providers-azure.md#atomic-publish-push--summary--replies) · [Gerrit](./gerrit.md#post-summary-comment) (unified `/review` is already atomic)

### Resolve Qodo Review Comment

After posting the summary, resolve the main Qodo review comment. **Gated on `AUTO_RESOLVE` from Step 5**: if `true`, run the resolve/mark-fixed command; if `false`, run only the 👍 reaction (acknowledgment without losing thread context for human readers).

**Steps:**
1. Fetch all PR/MR comments
2. Find the Qodo bot comment containing "Code Review by Qodo"
3. Resolve or react to the comment
- [GitHub](./providers-github.md#resolve-qodo-review-comment) · [GitLab](./providers-gitlab.md#resolve-qodo-review-comment) · [Bitbucket](./providers-bitbucket.md#resolve-qodo-review-comment) · [Azure DevOps](./providers-azure.md#resolve-qodo-review-comment)

### Create PR/MR

If no PR/MR exists for the current branch, create one. The user chooses between draft or regular mode — add the `--draft` flag (or Bitbucket's `[DRAFT]` title prefix) when creating in draft mode.
- [GitHub](./providers-github.md#create-prmr) · [GitLab](./providers-gitlab.md#create-prmr) · [Bitbucket](./providers-bitbucket.md#create-prmr) · [Azure DevOps](./providers-azure.md#create-prmr) · [Gerrit](./gerrit.md#create-change)

### Mark PR Ready for Review

After all fixes are applied, if the PR was created as a draft, optionally mark it as ready for review.
- [GitHub](./providers-github.md#mark-pr-ready-for-review) · [GitLab](./providers-gitlab.md#mark-pr-ready-for-review) · [Bitbucket](./providers-bitbucket.md#mark-pr-ready-for-review) · [Azure DevOps](./providers-azure.md#mark-pr-ready-for-review)

## Error Handling

### Missing CLI Tool

If the detected provider's CLI is not installed:
1. Inform the user: "❌ Missing required CLI tool: `<cli-name>`"
2. Provide installation instructions from the per-provider Prerequisites section
3. Exit the skill

### Unsupported Provider

If the remote URL doesn't match any supported provider:
1. Inform: "❌ Unsupported git provider detected: `<url>`"
2. List supported providers: GitHub, GitLab, Bitbucket, Azure DevOps, Gerrit
3. Exit the skill

### API Failures

If inline reply or summary posting fails:
- Log the error
- Continue with remaining operations
- The workflow should not abort due to comment posting failures
